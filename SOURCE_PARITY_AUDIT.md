# Original MiniDAYZ → Nintendo 3DS source-parity audit
**Status: FAIL — NOT identical.** This is a source-oriented audit ledger, not a certification of complete behavioral parity. Checked against the root `data.deobfuscated.js` extraction, the current `main` C++ implementation, and the supplied emulator/original-game screenshots. The 3DS's 400×240 top screen and 320×240 touchscreen legitimately require UI adaptation; mechanics, event timing, positions, image identities, item effects, and state transitions still need source-equivalent behavior.

## Source of truth and audit methodology
- `data.deobfuscated.js`, `c2runtime.js`, `mp_itemtable.js`, original `assets/gfx/`, the English localization XMLs and original audio files are authoritative.
- `data/stage1/stage1_manifest.json` records **1,429 objects, 8 layouts, 6 event sheets, 22,343 event nodes, 6,338 animations, 14,505 image frame references, 489 audio resource entries**. These are **extracted-data counts, not executed-function counts**.
- `tools/stage1/validate_stage1.py` checks whether the extracted Construct project and source snapshot match the root `data.deobfuscated.js`. This validates extraction, **not** the C++ port's behavior.
- **Provenance inconsistency:** the manifest's `source` label reads `Minidayz-Multiplayer-main/data.js` while the active validator checks root `data.deobfuscated.js`. Confirm the provenance of the archived manifest and regenerate its description from the root source; this discrepancy alone does not prove the current extracted JSON is from the wrong version.
- Compilation, unit tests, and the number of preconverted PNGs cannot establish pixel-perfect rendering, original game timing, correct spawn distribution, or event parity. Compare deterministic source event traces and capture actual 3DS frames.

## What the original screenshots establish
- **Menu:** Original MiniDAYZ+ reference has layered battlefield/city artwork, logo and distinct Continue, New game, Achievements, Unlocks, Options controls. Adaptation to 3DS can relocate controls, but omission of original menu functionality is not parity.
- **Gameplay:** Reference has populated streets, zombies, vehicles, buildings, on-screen HUD and equipment interactions. A sparse, differently generated native viewport cannot be called the same game.
- **Inventory:** Reference uses parchment-textured equipment cards, item durability/heat/armor text and a distinct original backpack panel. The earlier native cyan slot grid was visibly different; newer parchment renderer code still requires an emulator check.
- **Spawn:** Original start event expressions are known. Rejection/relocation in the C++ version requires separate proof that it preserves source spawn behavior.
- **Speed:** User observed approximately 10-FPS-feeling motion. Do not attribute the slowdown to one cause without actual frame timings and call counts.

## Verification requirements to close every row
1. Extract one documented source event/condition/action trace for **each** subsystem. Reference original event UID, object/animation ID and expected state change.
2. For a fixed source-compatible RNG seed or controlled random draws, compare original and native world-generation outcomes: start position, road grid, buildings, forest/water, loot, zombies and transition spawns. Verify source-specific branches and location conditions.
3. Compare original idle/walk/run/weapon frame sequences, speed, object hotspot and camera coordinates over matching real-time intervals.
4. Rebuild 3DS inventory to follow original slot behavior, exact artwork, equipment bonuses, durability and condition-dependent use, adapted to 320×240 without silently removing mechanics.
5. Map every relevant original audio trigger to a real native event, with expected clip and state; test pause and overlapping audio.
6. Verify all gameplay loops: damage, weapons, projectiles, melee, zombies, other NPCs, crafting, vehicles, death, saving/reload and cross-map progression.
7. Run real Manic Emu/new hardware comparisons with **frame-time instrumentation**, screenshots and input traces at matched positions. Set objective FPS and per-frame budget tests. Do not mark complete based on CI alone.

## Sign-off rule
For each row, record: source event UID/file and branch conditions; C++ function and test; source input state and RNG; expected/actual values; screenshot/audio evidence where applicable; performance result; **PASS / FAIL / NOT TESTED**. Until all core rows pass, report **NOT IDENTICAL / PORT IN PROGRESS** rather than “100% complete.”

## November 19, 2026 remediation started
- Committed a bounded heap-resident cache for authored procedural ground-scatter results. This avoids regenerating each visible marker's 33×33 tile choices every frame; source-specific condition gaps remain.
- Removed non-original retry, collision rejection and +/- offsets from the first-spawn formula; exact browser RNG behavior is still pending.
- Moved movement/NPC frame-time caps to 250ms, preserving 200ms frames in the player movement tests instead of discarding elapsed movement time.
- Exposed a SELECT-toggle overlay with **uncapped measured FPS**, frame milliseconds and runtime sprite-sheet reloads for diagnosis in Manic Emu.
- Added source item Heat/Armor readouts to worn-item parchment cards. The full original inventory interaction design is still unverified and not signed off.
- **None of these fixes proves original behavioral equivalence until a new emulator video and performance trace confirm them.**

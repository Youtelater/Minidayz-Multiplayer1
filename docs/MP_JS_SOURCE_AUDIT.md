# MiniDAYZ 3DS — audit of every `mp_*.js` script
**Verdict: 21 distinct root scripts, 21 identical copies in `Minidayz-Multiplayer-main/`. All 42 paths were accounted for.** The copies have matching Git blob SHAs. We inspected their browser entrypoint, decoded their escaped JavaScript symbols, and checked the behavior families in each file. This is a **code provenance and reuse audit**, not a claim that any module runs on a native 3DS.

## Critical distinction: base game vs multiplayer mod
- The root `index.html` explicitly identifies this package as a **test multiplayer version** with MPMod authors and compatibility warnings. Its script block loads `c2runtime.js` first, followed by all 21 `mp_*.js` helpers and networking libraries (PeerJS etc.). This is evidence that the `mp_` modules are **multiplayer additions around Construct 2**, not 21 missing parts of the original single-player Construct event code.
- The original core gameplay still lives in **`data.deobfuscated.js` + `c2runtime.js`**, with image/animation references under `assets/gfx/`. The `mp_` modules include legitimate extra gameplay information and infrastructure for the **multiplayer variant**, but must not silently overwrite original single-player rules.
- The JavaScript is obfuscated, including `\\uXXXX` Unicode-escaped property names. Our audit reads those strings statically and **never executes** the scripts, browser DOM calls, storage, networking, or modified RNG.
- The alternative folder is **not a newer source of unique multiplayer code** for these 21 files: byte-for-byte duplicate. Use **root originals** consistently, as requested.

## Where this changes the original-fidelity priorities
1. **Inventory and image mapping:** The authoritative native item icon generator is already based on `mp_itemtable.js`, not guessed PNG names. Audit `MDZItemVariants` and `MDZPlayerDropTable` for remaining missing icons, equipment visuals and drops. The original source event conditions still govern item gameplay.
2. **Menu:** Compare `mp_menu.js` artwork and UI labels with `Menu_Events` from `data.deobfuscated.js`. `mp_menu.js` is principally a **multiplayer browser menu**; its CSS is not an equivalent native 3DS boot implementation. Use `assets/gfx/menu_btn_wood-sheet0.png` / `options_menu-sheet0.png` (both present), not nonexistent `images/` duplicates.
3. **Terrain, map and spawning:** `mp_worldseed.js` supplies precise names of generation calls and a **hash-based test method**. This can improve port validation and reproducibility, but doesn't resolve the Construct random-expression order or missed SetTile commands by itself. The original source is primary.
4. **Player, NPC, combat:** `mp_players.js`, `mp_entities.js`, `mp_events.js` and `mp_throwables.js` help enumerate networked animation/equipment and attack states. Treat these as a **cross-check** only and back each original gameplay implementation with its Construct event UID.
5. **Save and eventual multiplayer:** `mp_worldstate.js`, `mp_join.js`, `mp_playerstore.js`, `mp_authority.js` describe an expected networked state model. Their browser APIs do not exist on 3DS; plan a separate native transport and deterministic serialization layer after single-player parity.

## Technical notes / audit boundaries
- Script load order in root `index.html` is part of the mod's dependency graph; do not reorder it blindly.
- `mp_menu.js` depends on `MDZLang`, `MDZHostSetup`, `MPTransport`, Construct runtime and browser DOM/localStorage. Copying it into the 3DS game would neither compile nor preserve single-player behavior.
- `mp_worldseed.js` instruments functions named in original source generation and is useful for reference **only after** confirming their call semantics against the corresponding source event UIDs.
- All 21 files are protected by `tools/stage1/audit_multiplayer_scripts.py` for source hash, mirror parity and browser load-order inventory. The script decodes Unicode escapes statically and never evaluates the JS.
- **Verdict:** the files **matter**, especially for icons, multiplayer menu styling, runtime compatibility, skins and world sync. They are **not a substitute for** the original single-player game code, and importing all of them as vanilla logic would make fidelity worse.
